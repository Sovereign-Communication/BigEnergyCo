# Harness v0.5.0

The first published `sovereign-harness` distribution: a cost-bounded,
stdlib-only verification and coding harness with consent, continuation, and a
verifiable participation ledger.

## Install

```bash
pip install sovereign-harness
harness --help
```

The import name is `harness`; the distribution name is `sovereign-harness`.

## [0.5.0] — 2026-10-25

### Verified

- **Paid default-attestation path, end to end.** A real one-node
  `plan --execute` on the paid lane landed a semantic edit with the independent
  verifier's `allow` (`openai/gpt-5.6-sol`), JEV `supported=0.97`, final gate
  `add-ok`, a 13-row chain-verified ledger, and **$0.004061** total cost. The
  same path at a $0.08 ceiling first exposed the verifier's 4096-token reserve;
  the fix below and its re-run are the release receipt.

### Fixed

- **Default-on diff attestation no longer reserves a whole-file output budget
  for its verdict (#388 follow-up).** The independent verifier was called with
  the apply request's `max_tokens`, which planned nodes leave at the 4096-token
  whole-file default; on a frontier judge that priced the verdict at $0.085755,
  more than an entire $0.08 plan run. A live `plan --execute` therefore paid for
  the apply call and the JEV gate, then refused the write at the verifier
  preflight. The verifier's own output budget is now bounded at
  `ATTEST_MAX_TOKENS = 1024` (a smaller caller pin is still honored), and its
  reported cost is recorded on the `diff_attestation` ledger row. The gate still
  sees the exact resulting bytes and still fails closed on deny, unparseable
  output, or transport failure. Re-run on the same fixture at the same $0.08
  ceiling: 1/1, verifier `allow`, JEV `supported=0.97`, final gate `add-ok`,
  $0.004061 total.
- **CLI `plan --execute` now gates every node.** `_plan_compose` did not pass
  the tree root to the composer, so the CLI planned `local_gate: null` for every
  node; on a fresh ledger the write-time trust gate refused the first write as
  ungated and a two-node plan completed 0/2. The CLI now roots the plan at its
  CWD, matching the HTTP and MCP faces, and each node gets the gate derived from
  its own target.
- **MCP gates no longer inherit the JSON-RPC stdin pipe.** `osal.run` passed
  `stdin=None`, so every verify gate inherited the MCP server's stdin — the
  stdio protocol channel — and blocked until the 300 s gate timeout. Gates now
  get `subprocess.DEVNULL` when no `input_text` is supplied (the isolation
  `run_tree` already documents); explicit input still uses the pipe.
- **HTTP plan runs reach the composer again.** `run_plan_task` called
  `compose_plan` with a positional goal and an unknown `settings` kwarg, so every
  HTTP plan failed with a `TypeError`. It now passes `opts_goal`, the session
  ledger and the options the keyword-only composer accepts.
- **HTTP/MCP dogfood use the documented 500-line default.** Non-CLI callers do
  not pass `max_lines`; the service forwarded `None` and the engine compared it
  with a line count. `run_dogfood` now defaults to `MAX_FILE_LINES`.

### Added

- **The assistant can propose and use a governed script (`SCR-3`).** SCR-2 made
  scripting a tool a human types; this closes the capability gap without adding a
  second runner. A chat reply may carry one marked `harness-script` fence (or a
  `SCRIPT PROPOSAL:` line above a Python fence); `extract_model_proposal` ignores
  ordinary code examples and ambiguous multiple proposals, and the chat lanes turn
  the reply into the same consent card (`kind=script`, `script_state=proposed`,
  `origin=model`) instead of saving a prose answer. Approval still runs exactly the
  bytes the card showed. After a model-origin run, one follow-up completion answers
  the original request with stdout/stderr attached in the system prompt inside
  `<untrusted-script-output>` — data-only, bounded, closing tag neutralized, and
  unable to propose another script, so execution cannot chain. The GUI posts the
  origin and renders the answer below the receipt, live and from history. The
  human `/script` path is unchanged and still ends at the receipt; scripting
  remains off by default.
- **Governed scripting reaches the chat box and MCP (`SCR-2`, #357).** `harness/script.py`
  stays the one execution owner; the new faces are thin. A chat message that starts with
  `/script` is parsed and _proposed_ — the source is compiled, shown with its sha256 in a
  consent card, and nothing is written or executed until the operator approves those exact
  bytes; the proposal makes no provider call. Approval posts kind `script` to `/api/runs`,
  and `script_start`/`script_end` land as steps with a receipt (exit code, duration, stdout,
  stderr, sha, Jev alignment) in the same message, stored with the turn as `kind=script`
  evidence in the same vocabulary as web sources. MCP clients list and call `script_run`
  over stdio; disabled, no-consent, missing-sha and sha-mismatch calls refuse with
  `errorKind: "script_refused"` (a mismatch is hostile trust evidence). `osal.run_tree`
  gained an optional `cancel_check`, so Stop kills a script's process tree (exit 125) the way
  it stops a provider call. `tests/test_script_faces.py` covers the trigger, refusals, MCP
  loop and dispatch; the plan was scored through the Jev pack at `answer_sufficient` 0.87
  against the 0.70 bar before implementation.
- **Governed scripting (`harness script`, `harness/script.py`).** An agent lane can now
  author and run one Python script for the current request — scrape a page, parse a file,
  drive Playwright, compute a result — instead of needing a new tool per task (the shape
  Prime Agent made popular: one execution surface, the model's own code). Off by default
  (`HARNESS_SCRIPT_ENABLED=1` opts in); consent is bound to the source sha256; the script
  runs in the selected workspace with a scrubbed environment (no provider keys), a hard
  wall-clock bound that kills the process tree, and a capped output. `--score` asks Jev
  whether the script aligns with `--goal` (sufficiency probability, recorded on the
  receipt, never used as the sandbox).
- **The Jev judge now sees the answer it judges.** `evaluate_answer` clipped the candidate
  to 1,800 characters independently of its input budget, so a complete 4,000-character
  audit was judged by its opening paragraphs and scored `answer_sufficient` 0.30 → the run
  reported `needs_iteration` on a good answer. The field caps now share one 4,096-token
  budget (`JEV_ANSWER_MAX_CHARS` 7,000), and a live re-score of the same plan moved 0.61
  → 0.81 and 0.23 → 0.81 (twice, deterministically).

- **Dynamic model rotation is now wired.** `rank_models_dynamically` shipped with the
  Dynamic Resource Allocation Engine but had no production caller and no producer for its
  `health_status` input, so the dynamic-model half of the engine was inert. `harness/router.py`
  now keeps a per-model health registry (`note_model_result` / `model_health`) and serves the
  four rotation pools through properties that delegate ordering to the ranker once a model in that
  pool has an observed outcome; `harness/apply_policy.py` records every terminal attempt outcome
  (HTTP error, paid BYOK, reasoning-only, readiness defer, success) into it. The declared head of a
  pool is never displaced, so DF-LING-2 (in rotation, never default) and the cheap-first
  discipline still hold, and a pool nobody has observed yet is served exactly as declared.
  16 hermetic tests in `tests/test_router_dynamic_rotation.py`.

- **Native driver module (`driver_core/`, `DRV-1`)** — a self-contained, standard-library-only package (verified extraction, Jev decision, deterministic action) reached through the existing `harness/perception_client.py` adapter, with a `driver-core` entry point, loopback REST under `/api/driver/*` (`health`, `vocabulary`, `schemas`, `verify`, `step`, `start`, `drive`), a Driver pane, and the MCP tools `driver_step`/`driver_health`/`driver_vocabulary`/`driver_verify`. Every synthetic input action (`click`, `type_text`, `press_key`, `focus`, `scroll`, `submit_irreversible`) is refused with `execution_refused` until an input backend is registered; nothing in this repository registers one, so `DRV-2` stays open. See `docs/driver.md`.
- **Jev spend and credit truth** — Jev input is priced at the verified $0.042/Mtok with the $5.00 monthly credit surfaced as a `jev` block on `/api/spend`, `/api/cost` and the cost report; legacy ledger entries priced at the old $42/Mtok are recomputed from their recorded input tokens.

### Fixed

- **`harness dogfood` reaches the verify phase again (#330).** The production
  seam passed `cancel_check=` into `_run_claims_verify`, whose signature did not
  accept it, so every run crashed with a `TypeError` after the ground phase. The
  seam now accepts and forwards the cancellation check, and a contract test drives
  the real `service.run_dogfood` → CLI seam wiring instead of patching the seam
  itself.

- **A refused script now closes its step (`SCR-2` follow-up).** A `/script` refusal
  used to end the run with `error_kind: script_refused` but no `script_end`, so the UI
  showed a step that never finished and had no receipt to render. Refusals now leave the
  same terminal evidence a successful run does: one `script_end` with `status: refused`, a
  typed `reason`, no invented exit code, and a receipt with the success shape (sha, goal,
  root, timeout, policy) built in `harness/script.py`. `run_script` and `propose_script`
  record it before re-raising, the server turns it into a `refused` turn that renders the
  same receipt card (so missing `allow_exec`, missing `consent_sha` and a sha mismatch are
  visible instead of a 400), and MCP pre-checks go through the same emitter while still
  returning `isError: true`. A successful run still emits exactly one `script_start` and
  one `script_end`; a refusal emits no `script_start`.
- **Secure workspace defaults** — GUI sessions no longer inherit the server's
  working directory, Auto Apply starts off, and file-bearing UI, agent, and MCP
  paths are resolved inside an explicit workspace or configured MCP root.
  Parent traversal, symlink path components, escapes, and obvious credential paths are refused
  or omitted from automatic context. This limits Harness-managed paths; it does
  not sandbox approved host verification commands.

- **Test isolation for subset test suites (#211)** — moved `test_agent` global patches into `setUpModule()` so importing `test_agent` does not pollute preceding test modules with disabled Jev keys or mocked governors during subset runs.
- **CLI escalation governance and HTTP worker resilience (#215, #219)** — added `--no-escalation` CLI flag and ensured `--max-rotations 0` prevents secondary model escalation; enforced `--task-max-cost` ceiling against actual spend in the escalation loop. Resiliently resolve `_http_worker.py` across temporary and moved checkout paths with safe cwd fallback, and allow weather query retrieval from `api.weather.gov`, `weather.gov`, and `wttr.in`.
- **Driver token and auth** — the in-process driver no longer uses a fixed fallback token: it uses `DRIVER_TOKEN` when declared and otherwise a random per-start token that is never placed in the environment or returned by an endpoint. A UI server started with a generated token no longer hands that token to whichever caller presents one first. A driver run's summary no longer reports success it did not observe: it reports `ok_steps`, says the goal was met only when the `verify` command passed, and reports `cancelled` runs as such. The UI server now accepts its token only from headers (never the URL), compares it in constant time, redacts `token=` from its log, closes the connection after a refused POST, and creates the desktop token file owner-only. `/api/driver/drive` no longer auto-grants consent by default (opt-in `auto_approve` grants only the read-only `observe` action, not labelled as a person), a passing `verify` with zero successful driver steps reports `verified_without_driver`, and `max_cost` is enforced. The test suite refuses any non-loopback network connection (`tests/__init__.py`), and the audit's R13 failure output now leads with the failing lines.
