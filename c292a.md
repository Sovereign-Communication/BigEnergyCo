## The only red check on merged `main` is this PR's subject -- and the gate is stricter than the body assumes

`main` at `551ce8f`, CI run `39989962080`: **6 of 7 jobs green**, `jev-complete` red with

```
score: 96.07 / 100  (target 95)  [FAIL]
6/21 proven · 13 at 85 · 2 at 60 (advisor 0.43, translation 0.54)
0/21 at the 0.95 confidence bar
```

That is the entire remaining gap to a green tree. Everything else in the project passes locally and in CI, on a clean checkout, with no edits.

### What actually fails

From `scripts/lib/jev-complete.mjs`:

```js
pass = allHard && combined >= target && blocking.length === 0
       && notProven.length === 0 && lowConfidence.length === 0;

const blocking = facets.filter(f => f.index <= doc.sentiment.blocking_max_index);      // ordinal 0
const notProven = facets.filter(f => f.index <  COMPLETE_EXIT_FACET_INDEX);            // 4 == ordinal 100
const lowConfidence = facets.filter(f => !(f.confidence >= COMPLETE_MIN_CONFIDENCE));  // 0.95
```

On this run: `allHard` true, `combined` 96.07 >= 95, `blocking` empty, `notProven` **15**, `lowConfidence` **21**. So it fails on the last two clauses, not on score and not on a blocking facet.

This matters for the proposal in this PR, and it is why the body's framing needs one correction:

**`improve_below_index` (85) is not the gate.** It only decides which facets get a `required_work` bucket. The pass predicate uses `COMPLETE_EXIT_FACET_INDEX = 4` (100) unconditionally, on every run, including the one attached to each push to `main`. So the option 1 as currently worded -- "every facet >= 85, translation named at 60" -- would not change this outcome by a single facet: 13 facets at 85 and two at 60 are all below 100, and `notProven` is still 15.

The aggregate is even more forgiving than that: `combined = 0.7 * mechanical + 0.3 * semantic`, and `mechanical` is 100 here, so the score clears 95 at an average facet ordinal of just **83.3**. One facet falling from 100 to 60 costs the aggregate 0.57 points (`0.3 * 40 / 21`). Today's run has thirteen facets at 85 (2.79 off) and two at 60 (1.14 off) -- 3.93 in total, which is exactly the 96.07 it reports, with 15 facets unproven. **Below all-100, the score is decoration.**

### What the three decisions now cost, precisely

| decision | what it changes in the gate | effect on `main` |
| --- | --- | --- |
| 1. staging floor 85 (translation named 60) | `improve_below_index` only, i.e. the report | **none** -- still red on 15 `notProven` |
| 1'. staging mode that relaxes `COMPLETE_EXIT_FACET_INDEX` for non-exit runs | new code: a run-scoped exit index, plus a pack that can say "staging" | green if the floor is <= 85 and confidence is handled |
| 2. confidence as telemetry | `lowConfidence` removed or scoped to exit runs | required for any green -- 21/21 today, and unreachable otherwise |
| 3. P10 boundary (exit-only 95/95/95) | the same code as 1' | this is the decision that makes 1' legitimate rather than a threshold cut |

The confidence half has never been met in the CI configuration: 147 facet-confidence samples across seven merged-main runs, none at or above 0.95; the series maximum is 0.90, and this run's is 0.86. (Corrected below: it is reachable, and that is worse -- a no-evidence live run put 6 facets above 0.95, one of them 0.97 on a verdict of "mixed".) The all-100 half is reachable in principle -- 6 facets are already there, `testing` reached it today on a test-only PR -- but not for `translation`, which stayed at 60 through Phase 3's specialised labels and Phase 4's deterministic term anchors, exactly as the judge's "native judgement" demand predicts.

So the real question in this PR is not which floor. It is **whether `main` is the program exit**. If it is, main stays red by construction and the honest move is to stop treating a red `jev-complete` as a release blocker while P10 is outstanding. If it is not, the PR needs the staging-mode code above, not a restated floor.
