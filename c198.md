## Car 3 closed: two real, two exonerated — with the code that decides it

Each item is answered with the question the lane review asked. Two were real defects and are fixed in #295; two are already guarded, and the guard is named rather than asserted.

### 1. `setupCitySearch` — `assets/js/sizing/location-picker.js` (p_real 0.55, race-stale-state 0.64)

**Question:** can async city-search results arrive after the input changed, showing stale results as current?

**Answered: no — 2026-10-23.** The lookup is generation-stamped. `lookupGeneration` increments on every input event, pick and resolution (`:88`, `:98`, `:55`), each async path captures `const generation = lookupGeneration` (`:106`, `:145`), and every landing site refuses to draw unless `generation === lookupGeneration && search.value.trim() === query` (`:112`, `:178`, `:198`). A superseded lookup is discarded twice over — by generation and by query text — so a slow reply for an abandoned query cannot overwrite a newer one. Regression test: `tests/location-picker.test.mjs` → *"a newer query resolves while an older lookup is pending"*, plus *"locateMe: a stale GPS refinement cannot overwrite a newer location choice"* for the same race through the geolocation path. The `listener-cleanup` pattern behind the flag does not accumulate either: `draw()` empties `list.innerHTML` before rebuilding, so the previous options and their handlers are dropped with their nodes.

### 2. `sendChatMsg` — `assets/js/chat.js` (p_real 0.54, unhandled-guard)

**Question:** can a message send actually race with incoming state updates, or is the flagged shared state effectively single-threaded here?

**Answered: yes, but not against incoming state — against a second send. Fixed in #295.** The browser is single-threaded, so no state update interleaves mid-function; the race is between two *calls*. Both appended to one chat window, both created a node with `id="loadingMsg"`, and `document.getElementById` returns the first. So the first reply removed the second's spinner, and the two answers rendered in whatever order they settled. The send path also cleared the input before the request went out, so a message typed while a reply was pending was swallowed.

The guard now sits before the input is read, so a refused send leaves the typed text in the box, and the flag is released on both terminal paths (`.then` and `.catch`) so the chat cannot latch shut. Covered by an **executed** test that drives the shipped function twice against a fake DOM and a held fetch: one request on the wire, the text preserved, one spinner, `chatHistory` unchanged by the refusal, and the guard released (the queued message sends once the first reply lands). It fails on the pre-fix tree.

### 3. `installNasaInterceptor` — `scripts/smoke/resilience.mjs` (p_real 0.54, tooling)

**Question:** does the interceptor leak across smoke runs?

**Answered: no — 2026-10-23, with one caveat stated.** `runTransportClassification` installs it and calls `net.release()` in a `finally` (`:523`), so a stage that throws cannot leave interception armed. `release()` drains every held request before disarming, sends `Fetch.disable` to the page **and** every attached session, and restores `ws.onmessage = baseOnmessage`. Across runs there is nothing to leak into: the closure, its `held` map and its `onmessage` hook belong to one CDP connection, and the next run builds a new one. Between modes the driver calls `releaseHeld()` rather than `release()`, which is deliberate — a full release unhooks the listener and only the first mode would be intercepted. The caveat: if a future caller installs the interceptor **without** a `finally`, the socket is still never left holding a paused request, because a dropped socket is drained (see item 4).

### 4. `send` — `scripts/smoke/runtime.mjs` (p_real 0.57, unhandled-rejection 0.73)

**Question:** is there a promise path here with no catch that fails a smoke run?

**Answered: yes. Fixed in #295.** At teardown. `close()` closed the socket while requests were still pending. Each pending promise kept its 30s timer, and when that timer fired there was no longer a caller awaiting it, so Node surfaced it as an unhandled rejection: the run died with a bare stack instead of the stage it was on — the failure mode the stage-name reporting exists to prevent. The same timers kept the process alive after the run had finished.

`close()` now drains the wire **before** the socket goes away, a dropped socket drains it too, and every settled request clears its timer. The drain lives in one exported helper, `rejectPending`, so the guarantee is testable without a browser: fake timers, three pending requests, one reason each, three timers cleared, second close a no-op.

### Result

Car 3's acceptance is met: each item fixed with a regression test or exonerated with a named guard; shipped-code items first. CI on #295 carries the proof.
