### The defect: every cold fetch leaked an open IndexedDB connection

`idbPut` and `idbDelete` in `assets/js/sizing/nasa.js` did:

```js
await idbReq(tx.complete !== undefined ? tx.complete : tx);
```

`IDBTransaction` is not a request. It has no `complete` property and never fires `onsuccess`; it completes through `oncomplete`. In a browser the left side was always `undefined`, so `idbReq(tx)` attached handlers the transaction never calls, and the promise stayed pending forever. The write still landed — `put` is queued synchronously and both call sites are fire-and-forget `.catch()` — so nothing looked broken. What never ran was the `db.close()` after the await: **one open connection leaked per cold fetch**, and a browser that exhausts its connection budget refuses the next upgrade.

Two more leaks were in the same three functions: `idbGet`, `idbPut` and `idbDelete` all returned early when the object store was missing, before their `db.close()`, and `idbDelete`'s handle was `const`-scoped inside the `try`, so a `finally` could not have closed it.

The fix is `txDone(tx)` on `oncomplete`/`onerror`/`onabort`, plus one `finally { db.close() }` per function so every exit closes — success, early return and failure alike. Semantics are otherwise unchanged: best-effort, fire-and-forget, `fromCache` on restore.

### Why nine green tests missed it

The double exposed `complete: Promise.resolve()`, which `idbReq` waits on just as fruitlessly. **The mock agreed with the bug**, so the suite certified a path that never completed. It now models the platform: no `complete`, `oncomplete` fired on the microtask after the write. That single change is what makes the defect visible — and it is the general lesson for the rest of this car: a double that is more forgiving than the platform certifies whatever the code does.

Three tests now count connections (`idbOpen()` opens a fresh request every call, so opens-minus-closes is the only witness):

- `a compact write closes the connection it opened`;
- `a storeless database is closed, not abandoned on the early return`;
- the existing stale-window test additionally asserts `closes() === opens()`, which covers `idbDelete`.

All three fail on the unfixed tree with `every opened connection must be closed, or the browser leaks one per fetch`.

### The one real defect: `createMapProviderRegistry`

```js
      if (!provider) return null;
      active = provider;                    // installed here
      return provider.init(options);        // init can reject
```

A blocked leaflet CDN is the concrete case — it is *why* the map is optional. With `active` set before the await, a rejected init left the provider installed: `onClick`, `drawRectangle` and `drawPolygon` reached a map that was never created, and `drawRectangle` returned the provider's result as though the map existed. `active = provider` now happens after the await resolves.

The single shipped caller (the roof-area map in `ui.js`) calls `cleanup()` in its `catch`, so no visitor-visible behaviour changes — which is why this is recorded as a contract violation rather than a shipped bug. The invariant belongs to the registry; the next caller should not have to rediscover the compensation. Failing-first proof: on the unfixed tree `drawRectangle` returns `{ok:true}` after a rejected init; on the fixed tree it returns `null` and the provider sees no call but its own `init`.
